# Stable Classic EF inbox identities

Classic EF inbox deduplication now uses the configured stable bus persistence identity, rather than the bus assembly/type name. Configure typed buses through `AddViciOneServiceBus<TBus>(persistenceIdentity: "...", configure)` and pass that bus's matching registration context to `UseEntityFrameworkOutbox`. The default bus uses `default`. Routing and the separate InMemory/Reliable-inbox identity algorithms are unchanged. A context without a configured stable owner is rejected on the Classic EF path.

Keeping the namespace, consumer/message contracts and endpoint address unchanged preserves deduplication across bus CLR-type renames. Different namespaces represent independent owners. Changing consumer/message names or endpoint addresses still changes their deduplication identity and requires a separately confirmed mapping.

Existing hashes contain no recoverable owner provenance. Do not silently adopt retained rows into another namespace. Before an upgrade, export the old package/schema snapshot and complete retained consumer-identity inventory, take a verified backup, and stop all writers, inbox cleanup and outbox delivery workers.

For the standard Classic EF schema, calculate old and new IDs using `EntityFrameworkInboxIdentityMigration.CreateLegacyConsumerId<TConsumer,TMessage>` with the exact earlier runtime key and endpoint, and `CreateConsumerId<TConsumer,TMessage>` with the intended stable namespace and endpoint. Confirm each retained owner explicitly. Supply distinct `InboxConsumerIdentityMigration` assignments and every other retained owner in `explicitlyUnchangedConsumerIds` to `MigrateAsync` using a fresh dedicated relational `DbContext`. Dispose that context after success or failure.

The helper validates the entire identity inventory and rejects ambiguous assignments, chains, cycles, unknown retained owners, and legacy/stable rows for the same message before modifying data. It processes pages of 128 inbox rows in one helper-owned serializable transaction, preserving received/consumed/delivered timestamps, expiry, lock, receive count and delivery sequence. Outgoing message foreign keys are reparented; their payloads and metadata remain unchanged. Inbox surrogate IDs and generated row versions are replaced. An already migrated, explicitly assigned inventory can return zero changes.

Custom inbox columns, inheritance, global filters or additional foreign keys require an application-owned migration. The helper rejects these models instead of losing data or disabling constraints. A complete plan of more than 4096 identities, including replacements, requires an application-owned bounded procedure. Use a dedicated migration context with provider settings suitable for a caller-managed transaction; the helper performs no provider execution-strategy retries and no schema deployment. This operation is an offline maintenance tool, not a startup hook or background service. If commit or disposal reports an error, independently verify the retained inventory before retrying: the database may already have committed.

After commit, independently verify the complete retained progress fields, row counts, outgoing message contents and foreign-key linkage through a new context. Start the new deployment and resend a retained message ID: the same stable owner must suppress its business operation while another namespace remains independent. Keep the backup and cutover inventory until this check is accepted. Rollback after writers restart requires the agreed recovery plan; reversing GUIDs alone cannot undo newly processed business operations.
