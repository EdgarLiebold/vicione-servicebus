Two independent read-only adversarial reviewers found three concrete defects. First, `ValidUntilUtc` is only metadata: Azure does not expire a blob from that property, `GetAsync` ignores it, and no cleanup reads it. An expired blob remains retrievable and stored. The PO has been asked whether Azure TTL must be fully enforced; this finding is **open**. Second, a SAS-backed client returned and logged a signed blob URI as its claim-check address. A unit regression failed before the fix with `?sig=SignatureOne` in the returned URI. New addresses omit the query; legacy signed addresses can still be read after SAS rotation using the current client credentials, while logs omit the old signature. Third, parallel compressed uploads to the same generated name reused block IDs, allowing one upload to commit another's staged bytes. A new unit regression failed before the fix because the IDs overlapped; each attempt now uses a random fixed-length prefix. Both reviewers re-reviewed these fixes and found no further concrete issue within the checked boundary.

The `TimeSpan.MaxValue` sentinel disagreed with the Core InMemory/FileSystem repositories. A new test failed before correction because Azure rejected it as timestamp overflow; it now leaves expiration metadata unset. A new Azurite test for both compression modes verifies that upload starts at the caller stream's current position and leaves the stream open.
