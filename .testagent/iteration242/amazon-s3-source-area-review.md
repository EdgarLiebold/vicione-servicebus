# Amazon S3 MessageData source area · iteration 242

All six current `src/Persistence/ViciOne.ServiceBus.AmazonS3` files were read in full with their own Unit and LocalIntegration tests. The project file already has a current-byte admission/disposition pair in the main source packet. The other five files are paired in `amazon-s3-source-admission.tsv` and `amazon-s3-source-dispositions.tsv`. These are bounded source-area decisions, not a product-wide A+ acceptance.

The adversarial review found two product defects. `PutAsync` used the short `TransferUtility.UploadAsync` overload, which closed the caller-owned input stream and reset a seekable stream before upload, contrary to `IMessageDataRepository`. The new LocalStack test failed before the fix with `source.CanRead == false`; the explicit upload request now sets `AutoCloseStream = false` and `AutoResetStreamPosition = false`. A separate all-object S3 lifecycle rule also expired uploads made with `timeToLive: null`. The PO selected unbounded null retention. New explicit-TTL uploads receive the product-owned lifecycle tag; null-TTL uploads receive no tag, and the owned lifecycle rule filters on that tag.

An existing product-owned rule with a prefix or all-object filter cannot be silently replaced: earlier objects have no tag, so replacement would stop their previous expiration. Startup now rejects that rule with a migration message for both configured and null lifecycle options, without modifying it. An existing rule already filtered by the product tag is left intact when the current options do not manage an expiration. Foreign rules are preserved during configured-rule reconciliation.

## Existing-bucket migration boundary

The repository deliberately does not rewrite an untagged product-owned lifecycle rule. Before enabling the new version on an existing bucket with that rule:

1. Stop writes and inventory the rule and every current object. Decide which existing objects must retain expiration. The old all-object rule applied to both explicit-TTL and null-TTL uploads, so their original caller intent cannot be reconstructed from S3 tags alone.
2. Add the product tag `vicione-servicebus-message-data-expiration=enabled` to objects that must retain expiration, preserving their other tags. Verify the inventory and tags before changing the rule. Resolve objects that cannot take another tag and any versioned-object policy separately.
3. Change only the product-owned rule with that ID to a tag filter with the selected whole-day expiration; preserve foreign rules. Verify the resulting rule and start the repository. The repository then accepts the canonical tag-filter form and tags only new uploads with explicit TTL.

This runbook is not an automated migration or a real AWS proof. Real lifecycle deletion, large-object multipart upload and customer IAM remain external gates. Startup now needs `s3:GetLifecycleConfiguration` even when `LifecycleExpirationDays` is null, so absence of that permission fails startup. Configured expiration also needs `s3:GetBucketVersioning` and requires a bucket where versioning was never enabled; that state cannot be restored after versioning was enabled. Explicit-TTL uploads additionally need `s3:PutObjectTagging`; this is required by the AWS `PutObject` API when tags are supplied. The bucket owner must keep versioning disabled after startup, because an external configuration change between inspection and upload cannot be made atomic by this adapter. No remote AWS operation was run in this iteration.
