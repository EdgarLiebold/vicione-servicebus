## Source-path and feature-loss checks beyond the signature

1. B1/B2/B3/B4 all add a singleton `PostgreSqlSendFailureClassifier` via `TryAddEnumerable` and then defer `UsePostgreSql(...)` to `SqlRegistrationBusFactory`. The classifier's typed exception-chain behavior has direct tests, and all four registrations have a singleton-registration assertion. Those tests do not prove all deferred factory paths. B4's `dataSourceProvider(context) ?? throw` failure path is currently test-unmapped. An API simplification must preserve per-bus context-dependent data-source selection if that capability is retained.
2. H1/H2/H3/H4 materialize `PostgreSqlHostConfigurator`/`PostgreSqlHostSettings`, invoke the optional callback, and call `configurator.Host(settings)`. Internal tests prove multi-host, explicit/default port, IPv6 and connection-string replacement; the H2/H3 integration paths validate transport use. H3's caller-owned `NpgsqlDataSource` uses `IsProvidedDataSource` to avoid disposal in `PostgreSqlDbConnectionContext.DisposeAsync`; the current H3 test does not observe the post-stop ownership boundary. H1/H4 lack positive public-route evidence.
3. M1 delegates to M2; M2 registers `PostgreSqlDatabaseMigrator`, validates `SqlTransportOptions` (address, port, connection limit) and migration options (at least one operation) on start, and registers `SqlTransportMigrationHostedService`. The requirement projection and startup tests support the validation claim only. Internal migrator/infrastructure integration tests establish SQL schema, role/credential handling, idempotency, notifications, queue/delivery and message-body behavior, not M1/M2 parameter mapping or hosted-service execution.
4. PostgreSQL send/publish/request work is observed in local integration tests, but `docs/provider-capabilities.json` explicitly marks durable-send dispatch **unsupported** for this transport. Do not re-label it accepted from normal send tests; no package-level A+ acceptance or suite carrier claim follows. A05's Suite carrier is RabbitMQ/InMemory, with PostgreSQL being a separate authoritative store. Removing this optional SQL transport would nonetheless violate the PO's full external-user capability boundary absent a new decision.
5. `AddPostgreSqlMigrationHostedService` is an `IServiceCollection` extension in `ViciOne.ServiceBus.SqlTransport.PostgreSql`, whereas `PO-2026-09-04-02` §6 asks DI extensions to live in `Microsoft.Extensions.DependencyInjection`. The four `UsingPostgreSql` methods are registration extensions in `ViciOne.ServiceBus.Configuration`; whether the same DI-namespace rule covers this bus-registration configurator also needs explicit Lead layering disposition. These are **candidate API-layer mismatches**, not authorization to rename mechanically: namespace migration needs a current/legacy consumer compile and API-baseline disposition. The bool overload's `create=false,delete=false` conflict and M2 XML's “optional” wording are concrete source/documentation inconsistencies to resolve.
