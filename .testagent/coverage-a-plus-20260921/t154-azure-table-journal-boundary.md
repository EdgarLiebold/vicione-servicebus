# T154 — Azure Table journal boundary and lease ordering

The Azure Table API review left two journal questions: whether the `IMessageJournalConfigurator` service-client overload uses its supplied table name, and whether an overfull partition is refused before any storage effect. The new positive composition test appends through that overload and reads the entry from the named physical table. A temporary wrong-table mutant (`OtherJournal`) failed exactly this test (10/11 in the journal class).

Adversarial review found a real product defect. With 99 existing journal entries and no capacity lease, `AppendAsync` formerly created a lease before discovering that the partition exceeded its 98-entry atomic repair limit. It threw, but left a new control row behind. The new overfull theory seeds 99 records both with and without an existing lease, then checks the exact entry IDs and the absent or unchanged lease. Against the old product ordering, only the no-lease case failed: the lease appeared after rejection (11/12). Shifting the bounds check from `> 98` to `> 99` also failed the corresponding new case (10/11 at that test count).

Commit `0719e0cb4` performs a side-effect-free bounded preflight only when the lease GET returns 404, before creating that lease. The authoritative entry snapshot still follows the lease ETag read. An initial fix that reversed those two operations was rejected by Red Team: a delayed writer could pair an old entry snapshot with a fresh lease ETag and exceed capacity. `DelayedLeaseRead_ReloadsEntriesBeforeCommittingAtCapacityAsync` deterministically gates the first lease GET, lets another append commit, then releases the first writer. The deliberately reversed source order produced two rows at capacity one (12/13); the final source retains one. The test always releases the gate and bounded-awaits the first task, including failure paths.
