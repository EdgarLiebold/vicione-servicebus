# T156 — SignalR remote group timeout timer boundary

The historical SignalR API review's requirement-mapping concern is stale: the current `SignalRBackplaneConfigurationTests` cases are present in `SignalRRequirements.json`, and option snapshotting already has a behavior test. Its upper-timeout question exposed a product defect. `SignalRBackplaneOptions.Validate` accepted every positive `TimeSpan`, but remote group requests use `ClientRequestHandle.StartTimeoutTimer` and ultimately `TimeProvider.System.CreateTimer`. A .NET 10 runtime probe accepted durations through `4,294,967,295 ms - 1 tick` and rejected `4,294,967,295 ms` and `TimeSpan.MaxValue` with `ArgumentOutOfRangeException` from the timer. Registration formerly accepted those unusable values, deferring the failure to a group operation.

Commit `be890afef` rejects durations at or above the first unsupported millisecond during `AddSignalRBackplane`, before service registrations. The new `Registration_RejectsTimeoutBeyondTheSystemTimerLimit` theory checks that the first invalid millisecond and `TimeSpan.MaxValue` fail without DI mutation. `Registration_AcceptsTheLargestSystemTimerTimeout` checks both the last whole millisecond and the last representable tick below rejection, including exact settings retention. The two invalid cases failed against the original source (21/23 focused cases); with the correction the focused class passed 24/24 and the complete SignalR project passed 101/101.

Independent read-only Red Team review found that the initial upper bound incorrectly rejected fractional milliseconds below the timer's first invalid millisecond. A direct runtime counterprobe confirmed the issue; the bound and positive theory were corrected. Final review is PASS with no concrete P1/P2. The first isolated receipt attempt built with zero warnings/errors but could not start MTP because the sandbox denied its named pipe. The approved rerun succeeded: `artifacts/t156-signalr-timer-boundary-approved/receipt.json` (SHA-256 `2b0d2793c353678687b0b5ac0a9f4ba2dec8e52bcce733b96d87ea164cce4389`) verifies 101/101 tests, 11 unchanged binaries and 1,422 tracked product sources at `be890afef`. This focused result does not establish a new product-wide Coverage/CRAP profile.
